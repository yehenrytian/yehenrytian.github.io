结论一：现有实现能快速接住新模型

Hy4 与已适配的 DeepSeek-V4 同族，稀疏注意力与索引器可直接复用；未新增任何算子即完成 tiny 规模的接入与数值验证，投机解码也只需补一处草稿层架构注册。索引器的候选数上限（256）也已解除，1024 / 2048 现已支持，同样没有新写 kernel。

结论二：顺带给现有实现做了一轮检查

真实权重比对暴露出一个索引器 kernel 的算错，它同时影响已适配的 DeepSeek-V4；另外两个平台级问题也是这轮发现并修掉的。三处修复的受益面都超出本模型，提高的是这个版本整体的可靠程度。

02
Challenge

适配难点：四个机制 + 两项外部困难

Hy4-preview 共 78 层、hidden 6144、权重分 131 个分片；模型卡给出总参 770B、激活 49B（不含 MTP 层）。相对已适配模型，它组合了四个机制。

机制 01
Gated 稀疏 MLA

DeepSeek-V3.2 系稀疏注意力，输出再过一道 sigmoid 门。头维 576（512 潜在 + 64 rope）、v 256；上游实现的后端与编译目标都限定在两代 NVIDIA 架构，IFWA 无法使用

机制 02
Lightning 索引器

先轻量打分选出 top-k 个 key，再做稀疏注意力。真实模型 index_topk=2048，而 IFWA 的 top-k kernel 上限是 256

机制 03
iHC 残差流

层间多路残差混合，hc_mult=4。上游为纯 torch fp32；DSV4 的同类 kernel 带 Sinkhorn，语义不同不能复用

机制 04
MoE + 截断激活

层 0 dense，其余 256 专家选 8 + 1 共享；激活带 swiglu_limit=10。上游把截断放进激活配置而激活名仍是 silu，IFWA 原先静默忽略

上游尚无实现 → 拿不到参考模型

hy_v4 不在 vLLM main 中，实现来自一个未合入的开放 PR；截至 2026-08-31，transformers 已发布版本与主干均无对应实现，模型仓也未随附可直接运行的模型代码。因此拿不到任何现成的参考模型用于整模型比对——而 IFWA 自己的稀疏注意力实现正是被测对象，不能拿来当参考。

版本跨度

该 PR 基于 2026-08-29 的 vLLM（026d5af7），IFWA 侧原先用的是 8 月 17 日的 53e211d29，相差 495 次提交；相对 IFWA 主线在用的 v0.25.1 则是 2056 次。本轮先升到纯上游版本、再叠加未合入的 PR，7 处接口差异逐项跟进。

Validation · Real Weights

真实权重验证：逐机制数据比对

切片怎么取

  • 同一 tiny 形状换成真实权重前缀切片：取源模型第 0 / 1 / 2 / 5 层——层类型必须与 tiny 配置声明的一致，否则加载即报错
  • 专家取前 16 个，词表缩到 512，落盘 113 个张量 / 20 MiB
  • 无整模型参考 → 拿真实激活在 CPU 上以 fp32 重算，再与设备结果比
  • 端到端：权重加载 2.4 s，输出 [481, 354, 294, 257]，两个独立进程一致；logits 有限、top-1 随步变化，可排除退化

「两进程一致」在贪心解码下只证明执行确定，不证明数值正确；数值结论来自右侧比对。

索引器候选数上限已解除，且没新写 kernel

原限制来自索引器现用的融合 kernel：它把打分与选择做在一起，选择部分用固定 256 长度的数组，超过就拒绝。不必为此重写——仓内本来就有一个与上游同源、无候选数上限的通用逐行 top-k 算子，索引器的另一条分支一直在用它。改法是让融合 kernel 在候选数超限时只输出分数，再交给那个通用算子。

验证分三层：通用算子补测 1024 / 2048，覆盖其内部三条处理分支，分数与参考完全一致；索引器既有 8 个单测改动后仍全过；端到端用 index_topk=2048 跑通，与 256 的基准逐 token 相同——tiny 序列短、选择退化为全选，本就不该变，这一层验的是链路接通且不改结果。

本轮改到 C++ 的两处，都不是新增算子

  • 本仓 csrc/：跟进上游一处接口变化（MoE 路由算子末尾新增一个参数），改 3 个文件 +258/−96，新增 .cu = 0，该算子单元测试 774 项通过
  • 共享子模块：修正索引器 top-k kernel 的计算语义，两个 .cu 合计 +41/−19，不计入上面的数字

三项契约回归全部符合预期

06
Findings

顺带发现的三个平台级问题

三者都不是 Hy4 引入的，影响面超出本模型。

01 · 索引器 top-k kernel 算错

漏了取正、漏了跨注意力头求和，且多个头会写进同一行输出——只在单头时才恰好正确。影响 Hy4（2 头 / 真实 32 头）与 DeepSeek-V4（tiny 检查点 64 头）。

已修正并验证：8 个单测全过，真实切片上 105 个需选择的行逐值比对 max|gap|/max|logit| = 0。

02 · 退出期崩溃

进程退出时设备上仍有未同步的任务。与模型无关——最小复现只需两次矩阵乘不同步直接退出。

已在插件初始化处用 atexit 注册退出前的整设备同步，无开关、对所有模型生效（执行体带可用性守卫，异常静默）。驱动侧的析构顺序问题记为待跟进。

03 · MoE 截断参数被静默忽略

上游把截断值放在激活配置里，而激活的名字仍写作普通 SwiGLU，IFWA 侧只看名字、丢掉了这个值。影响所有使用带截断激活的 MoE 模型。

已改为读取该值并调用既有的截断激活算子，单算子逐元素比对无差异。

为什么长期没被发现：Hy4 与 DeepSeek-V4 两边的端到端用例断言强度不同（前者断固定 token，后者只断退出码与 token 个数），但共同的根因是序列都远短于 top-k 上限，选择退化为全选——打分错了也不改变选中的集合。该缺陷是在真实权重比对做出来之后才暴露的，随附的 8 个单测也在那时补上。

Open Issues & Next

尚未解决的问题与后续计划

能力上限

  • FP8 变体跑不了：checkpoint 由 modelopt 产出，权重与缩放因子按它的约定存放，而平台声明能接的只有 fp8 与 deepseek_v4_fp8 两种存法，加载即被拒
  • 卡的是存法而非数值格式——MXFP8 与已支持的 DSV4 是同一类格式，后者能跑；要支持只需接一条 checkpoint 解析路径，不必动 kernel。结论来自代码核对，未实跑

未覆盖

  • 完整模型（78 层 / 770B）、图捕获、TP/EP
  • 整模型 logits 比对不可得：上游与 transformers 均无可本地运行的参考实现，需另立项
  • 上游那套可选加速算子库按 NVIDIA 架构编译，IFWA 用不了，缺失时自动回落
  • 其他已适配模型在新版本上的状态未测

待跟进 / 未合入

  • 退出期崩溃已用退出前同步规避，但根因在驱动侧的析构顺序：设备侧库的析构早于在飞 kernel 完成。已整理为 FINDING，目前无回复
  • 索引器 kernel 的两处改动位于共享子模块 third_party/deepseekv4，已推到特性分支但尚未合入主干；本仓记录的子模块版本仍指向改动之前的提交
  • 上游 Triton 算子带一个本平台不认识的启动参数，走到 Nova 就会报错；本模型路径不会走到，其他模型若走到会失败

优先项

① 把索引器 kernel 修复合入子模块主干并更新本仓引用——它同时修正 DeepSeek-V4 路径上的既有缺陷。② 为 DeepSeek-V4 补一次索引器数值比对：其端到端用例只断退出码与 token 个数，且序列过短使索引器退化为全选，两重原因叠加导致该缺陷长期无法被发现。

能力扩展

③ 整模型 logits 比对（需另立项搭建可运行的参考环境）。④ 图捕获、TP/EP、完整模型规模。
